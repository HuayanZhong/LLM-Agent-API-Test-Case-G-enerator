# 代码注释规则

目标：让审查者快速理解「为什么」和边界条件，而不是复述代码。默认偏多写关键注释，但每条必须短、具体、可审查。

## 一、必须写

- 非显然的业务规则或约束，例如「必须按正常现场顺序重放，否则复现不出来」。
- 关键分支的原因：为什么降级、为什么兜底、为什么这里重试。
- 不变量、前置条件、副作用：事务、幂等、并发、缓存、超时、状态迁移。
- 边界与失败路径：空值、超时、数据过期、对端无响应、权限不足。
- 外部依赖与安全边界：A2A、MCP、Supabase RLS、SSRF 白名单、密钥来源。
- 临时方案与待办：写清原因、负责人或 issue、移除条件。
- 公共 API / 模块入口的简短契约：参数、返回、错误、副作用，用 `/** ... */`。

## 二、不要写

- 复述代码或变量名，例如 `// 增加 i`、`// 返回结果`。
- 装饰性分隔线、作者、日期、变更日志。
- 注释掉的旧代码；删掉，用 git 历史。
- 每个字段、每行都塞 JSDoc；公开 API 之外不强制。
- 未经验证的猜测，或与实现不一致的旧注释。

## 三、写法

- 默认中文；标识符、类型、协议名、错误码保留英文。
- 一条注释说清一件事；超过两行，优先拆函数或写设计文档。
- 写「为什么 / 约束 / 后果」，不写「做了什么」。
- 动词开头或名词短语，不用客套话，句号可省。
- 行内注释放在被解释代码的上方；行尾注释只用于极短且无歧义的情况。
- 公共 API 用 `/** ... */`，内部实现用 `//`。
- 待办格式：`// TODO(owner): 原因 / 移除条件`；`FIXME` 同理。

## 四、密度

- 每个有决策的分支、每个外部调用边界、每个不变量，至少一条。
- 连续的、自解释的 CRUD 不强行加注释。
- 判断标准：审查者是否需要反推意图；需要，就补一条短注释。
- 「多写」指多写关键点，不是把一句话拆成三行。

## 五、示例

```ts
// 正常现场可能已过期：重放失败先判数据不可用，不直接报缺陷
if (!scene.isFresh()) return { status: 'DATA_STALE' };

// A2A 对端可能不回执；超时进入重试，不能直接判为已修复
if (task.isTimedOut()) return retryTask(task);
```

反例：

```ts
// 检查是否新鲜
if (!scene.isFresh()) { ... }

// 下面开始处理任务，首先判断是否超时，如果超时的话就重试……
```

## 六、审查清单

- 关键决策是否写了「为什么」？
- 失败路径、边界条件是否说明？
- 有没有复述代码或过时注释？
- TODO / FIXME 是否有负责人和移除条件？
- 公共 API 的输入、输出、错误、副作用是否清楚？
